# Qwen3-30B-A3B-Base ReTool validation on H100

Four independent continuous 50-step training runs, measured September 16–17, 2026. Each arm uses one 8×H100 80GB node. These results exercise the native SGLang lifecycle changes after [Dynamo PR #13951](https://github.com/ai-dynamo/dynamo/pull/13951); they are not an isolated KV-router ablation.

## GPU results

Every arm completed 50 steps and 12,800 trajectories with training exit 0, finite nonzero gradients, rollout/actor probability correlation above 0.98, and a complete checkpoint at step 50. Both Dynamo arms also passed the two-worker routing/KV-event checks. W&B tail metrics were reconciled from the completed local JSONL logs after SDK teardown failures; this only repairs logging, not training.

Dynamo/vLLM output-token throughput is **+3.9%**, with **4.6% lower** mean step time. Dynamo/SGLang output-token throughput is **10.4% lower**, with **2.8% higher** mean step time. These are observations from one training run per arm, without a statistical significance claim.

Output throughput is `sum(model-generated response_mask tokens) / sum(AgentLoopManager.generate_sequences wall time)`. Tool-return tokens are excluded from the numerator; tool execution remains in the wall time. Full-step timing includes actor work, weight synchronization, and checkpoint saves, but excludes model loading/startup. It is different from `perf/throughput`, which counts prompt and response-context tokens over full-step time per GPU.

The [200 per-step measurements](retool_h100_20260916.csv) and [aggregate checks and source-log hashes](retool_h100_20260916.json) allow recalculating these figures without W&B access.

## Validation scope

The GPU runs used the lifecycle/flush/serializer changes in this PR. Their launchers supplied `--engine-route flush_cache:tm` explicitly. The PR additionally makes this the recipe default and preserves explicit route overrides; those launch-configuration changes are covered by the CPU regression suite. A second set of 50-step GPU runs was not performed after this automatic-registration cleanup.

## Experiment prerequisites and limitations

The measured runtime was an experiment snapshot, not an otherwise unmodified checkout of the recipe and verl pins. It also included these independent training-side preparations, which are **not shipped by this PR**:

- Nonzero-rank FSDP2 meta initialization via an experiment-local model loader, to avoid loading the full 30B model on every rank.
- Configurable per-microbatch FSDP2 gradient synchronization, set to `defer_fsdp_grad_sync=False` to fit the model on H100.
- The matching SGLang 0.5.19 serializer import update in verl’s native SGLang adapter.
- Existing local ReTool dataset/tool integration and a SandboxFusion subprocess wrapper, shared across all four arms.

The full training runs validate this prepared environment; installing only this PR is not claimed to reproduce the H100 training setup. V1 async, multi-node rollout and the legacy optional parameter-readback diagnostic were not validated here.

Successful tool trajectories were sparse (2 / 2 / 4 / 3 out of 12,800, in table order). The runs establish executable training and lifecycle/refit behavior, but do not represent heavy multi-turn tool traffic. Generated lengths and evolving policies differ between arms. To isolate KV-aware routing, freeze a checkpoint and request trace, control cache warm-up and arrival concurrency, compare Dynamo round-robin with KV-aware routing, and repeat runs.

An earlier 10-step pilot had checkpoint saving disabled. It was not resumed or concatenated into these results; all four reported runs started fresh and completed 50 continuous steps.
